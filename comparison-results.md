## Developer Experience (manually maintained)

_This section is preserved across `pnpm compare` runs. Observations are first-hand,
from implementing the identical workflow in all three packages._

### Lit

#### Good
- Plain `tsc` build (~6 s, 28 files). No bespoke compiler, no generated code to reconcile.
- Reactive **controller** cleanly separates state/API from rendering — the element only renders and emits. Best-fit for an SDK where the workflow logic is the product.
- Shadow DOM style isolation for free.
- Hand-written React wrapper is genuinely thin (~40 lines) and produces the *exact* desired API: `onSuccess(result)`.
- One runtime dependency (`lit`); leanest footprint overall.

#### Bad
- Decorators need `experimentalDecorators` + `useDefineForClassFields: false` — a tsconfig gotcha that isn't obvious until it breaks.
- You wire the React bridge by hand (property assignment + event listener). Fine at one component, more boilerplate at scale.

#### Surprising
- How little there is to it. Element + controller + register + wrapper is a small, boring, legible surface — exactly what you want to distribute.

### Mithril

#### Good
- The framework-neutral `mountFunctionalAction()` → `{ destroy, update }` handle is a clean embedding boundary; the host never becomes a Mithril app.
- Smallest, simplest mental model for imperative mount/teardown; closure-based store keeps instances isolated with zero ceremony.
- Plain `tsc` build, fewest generated files (16).

#### Bad
- **Not a web component.** For a distributable framework-agnostic library, "mount into a node" is a weaker boundary than a real custom element — no declarative HTML usage, no attribute/property contract.
- No Shadow DOM → no style isolation. Had to inline styles per vnode to avoid leaking/inheriting host CSS.
- Global `m.redraw()` redraws every mounted root, and boolean attributes render as `""` (had to emit explicit `"true"/"false"` for `aria-pressed`).
- Largest runtime bundle of the three.

#### Surprising
- How well it *does* hide itself behind callbacks — the React bridge and the host truly never see Mithril. It's a good embedding tool, just not a good *web-component* tool.

### Stencil

#### Good
- Smallest gzipped runtime (7.6 kB) and a real compiled custom element with typed `@Prop`/`@Event`.
- `@State`-driven components are ergonomic to write; Shadow DOM isolation like Lit.
- The React wrapper is **generated** — no hand-written bridge to maintain as the component evolves.

#### Bad
- Heaviest toolchain by far: own compiler, a build that's **~4–6× slower** than the others (tens of seconds vs. single digits), 40 generated files, multiple output targets to understand.
- The generated React wrapper is *source that must be compiled* (extra `tsc` pass), it self-imports the package (needed a `./dist/components/*` export subpath), and it pulls in a `@stencil/react-output-target` + `@lit/react` runtime — more transitive cost than the hand-written wrappers.
- Generated event prop is `onFunctionalUiSuccess(event)`, not the ideal `onSuccess(result)` — the consumer unwraps `event.detail`.
- The integrated Jest test runner is **deprecated** (removed in Stencil v5) and didn't resolve the ESM workspace mock cleanly; the spec test uses a local mock.

#### Surprising
- The custom-element output is tiny and clean, yet the *packaging* around it (loader vs. custom-elements vs. lazy `.` entry, generated-then-compiled wrappers) is the most complex of the three to reason about — which is exactly the "what does the consumer download / import" question the POC set out to answer.

## Recommendation

**Lit is the strongest foundation for the production functional UI library.**

The library's job is to ship reusable, framework-agnostic UI that *owns workflow
logic* and can still offer excellent framework-specific integrations. Lit hits all
of that with the least accidental complexity:

- It produces a **real custom element** — the framework-agnostic boundary the SDK
  needs — the same as Stencil, but with a plain `tsc` build instead of a bespoke
  compiler that runs several times slower and a pile of generated, then-compiled, artifacts.
- Its **reactive-controller split** (state/API separate from rendering) is the best
  architectural fit for a product whose value *is* the workflow logic.
- The **thin hand-written React wrapper** delivered the exact intended API
  (`onSuccess(result)`) with one small file and one runtime dependency, whereas
  Stencil's generated wrapper gives an event-object callback and drags in extra
  runtime.
- **Shadow DOM** gives style isolation out of the box.

**Stencil is the runner-up**, and the right call *if* the library will grow to many
components across many frameworks and the team wants compiler-generated wrappers for
React/Vue/Angular at scale — accepting the heavier toolchain, slower builds, and more
opaque packaging as the price.

**Mithril is least suited to this specific goal.** It's an excellent *embedding*
tool — the `mount`/`destroy` handle hides the framework completely behind callbacks —
but "mount into a node" is a weaker distribution boundary than a custom element, and
the lack of Shadow DOM style isolation is a real gap for UI dropped into arbitrary
host pages.
